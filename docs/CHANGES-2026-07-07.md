# ShelterLink — Improvements (7 July 2026)

Summary of the work done to make ShelterLink reproducibly runnable, verifiable,
and more correct. All changes are in the `shelterlink cursor` copy (the newest).

## Headline: the app is now runnable from a clean checkout

Previously there was **no base database schema anywhere** — only incremental
migrations — so nobody could actually stand the app up without hand-building
tables. That gap is now closed.

### New: database build + sample data
- `database/schema.sql` — the full, authoritative schema reconstructed from the
  models: `users`, `opportunities`, `volunteer_profiles`, `applications`,
  `volunteer_hours`, and the session store, with keys, foreign keys, indexes and
  utf8mb4. (Badges are code-defined, not a table.)
- `database/seed.sql` — realistic animal-shelter sample data with **working
  logins** (real bcrypt hashes): admin `admin@shelterlink.org` / `Admin123!`,
  volunteers `Password1`.
- `scripts/setup-db.js` + npm scripts: `npm run db:setup` (schema only) and
  `npm run db:reset` (schema + sample data), driven by `.env`. No MySQL CLI
  needed.

### New: automated tests (zero new dependencies)
- `test/` suite using Node's built-in runner (`npm test`), with a mocked DB pool
  (`test/helpers/mockDb.js`). 40 tests covering model query/param construction,
  badge logic, application/cancel guards, field whitelisting, hours validation,
  CSV export, and controller-level rules (including regression tests for the two
  behavioural fixes below).

### New: end-to-end smoke test
- `scripts/smoke-test.js` (`npm run smoke`) drives the full lifecycle against a
  running server: register → profile → approve → create shift → apply → accept →
  log hours → approve → badges → CSV export, plus auth-guard checks.

## Bug fixes

1. **Registration silently dropped phone numbers, and two admin features were
   broken.** The registration form has a required phone field and the admin
   volunteers list + volunteer CSV export both query `users.phone`, but the
   column never existed — so phone was never stored and those two queries threw
   "Unknown column 'u.phone'". Fixed end-to-end: added the `phone` column
   (`database/002_add_phone.sql` migration + schema), stored it on volunteer and
   admin registration, surfaced it in the admin profile view, and added phone
   numbers to the seed data.

2. **Volunteers with `approved` applications couldn't log hours.** The codebase
   treats `accepted` and `approved` as the same state everywhere (capacity,
   badges, `spots_filled`), but `hoursController` recognised only `accepted`, so
   an `approved` volunteer was wrongly blocked from logging hours (and from the
   active-application count). Now both are accepted.

3. **You could apply to shifts that weren't open.** `applyForOpportunity` didn't
   check opportunity status, so a volunteer could apply to a `closed`,
   `cancelled` or `completed` shift. Now blocked with a clear message.

## Frontend audit (no changes needed)
- Cross-checked every frontend `apiRequest`/`fetch` call against the actual
  routes and controller-expected fields: all endpoint paths and payload keys
  match (register sends `phone`, hours sent as a number, applications send
  `opportunityId`, status updates use valid `accepted`/`rejected` values). Once
  the backend `phone` column was added, the registration → volunteers list →
  CSV export path is fully consistent end to end.

## Notes / follow-ups
- Verification here was done statically (SQL parsing, column cross-checks,
  referential-integrity checks, unit tests, hash validation) because a live
  MySQL server couldn't run in this environment. Run `npm run db:reset` then
  `npm run smoke` on your MAMP setup for the live end-to-end confirmation.
- There are ~6 duplicate project copies in the parent folder
  (`ShelterLink`, `ShelterLink 3`, `shelterlink cursor copy`, …). Consider
  consolidating to `shelterlink cursor` and archiving the rest.
